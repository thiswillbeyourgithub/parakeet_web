# 11.5.0 (2026-10-22)

## A faster CPU runtime, built for this app

On the processor (WASM) backend the app now runs its own build of ONNX Runtime 1.30.0 instead of the stock one. The stock runtime computes the quantized encoder's matrix products by first expanding the int8 weights back to fp32, which is where most of the encode time went; this build adds an integer kernel for those products (8, 4 and 2 bit) and is otherwise the stock runtime with every operator included. Through the real app, transcribing the 3-minute test recording on WASM int8 took a median 86 s against 144 s on the stock runtime in Chromium 156, and 66 s against 117 s in Firefox 157 (3 interleaved runs each, on a busy machine, no overlap between the arms), with 359 of 360 words identical to stock and the custom transcripts identical across browsers. Browsers with relaxed SIMD (Chromium, Firefox) get one build and the others a plain SIMD build; the file is chosen by feature detection, checked against the integrity manifest like every runtime file, and any failure (missing file, wrong hash, a runtime that cannot build a session) falls back to the stock runtime. The GPU backend keeps the stock runtime, so switching between the two now reloads the page once and resumes the load. A new **CPU runtime** setting (Optimized or Stock, under Model and performance) switches between them, and `?ortep=stock` in the address still forces stock and takes precedence. The README has the full story under "A CPU runtime built for this app".

## UltiMed repos renamed

The French medical fine-tune is now [Olicorne/parakeet-tdt-0.6b-v3-ultra-UltiMed-onnx](https://huggingface.co/Olicorne/parakeet-tdt-0.6b-v3-ultra-UltiMed-onnx) (was `parakeet-tdt-0.6b-v3-UltiMed-onnx`), and the redux hybrid is [Olicorne/parakeet-tdt-0.6b-v3-redux-UltiMed-experimental-onnx](https://huggingface.co/Olicorne/parakeet-tdt-0.6b-v3-redux-UltiMed-experimental-onnx) (was `parakeet-tdt-0.6b-v3-redux-UltiMed-onnx`), since it is a weight blend rather than a proper fine-tune. Hugging Face redirects the old URLs, and a visitor whose saved model was the old UltiMed id keeps it. The picker label is now `ultra-UltiMed`, and medical mode looks it up by that full label, so it still finds the right model when the redux hybrid is offered too. Operators should update `VITE_MODEL_REPO` and rename their local mirror folder.

## Speaker identification now uses NVIDIA's Streaming Sortformer

**Speakers** no longer uses sherpa-onnx (pyannote segmentation plus CAM++ clustering). It now runs NVIDIA's [Nemotron-3-Diarization](https://huggingface.co/nvidia/Nemotron-3-Diarization), exported for the browser as [Olicorne/Nemotron-3-Diarization-web-onnx](https://huggingface.co/Olicorne/Nemotron-3-Diarization-web-onnx), on the same ONNX Runtime as the transcription. A second ML runtime and its integrity pins have been removed from the app. The model tracks up to 8 speakers, numbered in order of first appearance. The speaker count you set is now a cap: the most active speakers are kept and each moment of a dropped one goes to the kept speaker the model rates most likely then, and changing it only regroups the existing result. Each backend downloads only its own precision: int8 (~100 MB) on the CPU, fp16 (~200 MB) or fp32 (~400 MB) on WebGPU. The ONNX graphs were checked against NVIDIA's reference forward, with 100% agreement on speech decisions for fp32 and 99.97% for int8 on a 114 s, 5-speaker clip. CAM++ is kept, but only to recognise a voice across recordings.

The diarization model is now prefetched only when **Speakers** is the default display. Otherwise it downloads on the first click.

The OpenAI-compatible server diarizes with the same model on its own ONNX Runtime. `PARAKEET_DIARIZE_SEG_MODEL` and `PARAKEET_DIARIZE_EMB_MODEL` are gone, so old configurations that set them are now silently ignored. They are replaced by `PARAKEET_DIARIZE_MODEL` and `PARAKEET_DIARIZE_PRECISION`. `max_speakers` is a cap, and `min_speakers` is ignored with a warning. Self-hosters: `VITE_DIARIZATION_REPO` now actually works (it was read but never wired), and the diarization variables now reach the Docker container. Written with Claude Code.

## Medical terms are corrected too

The **Drugs** view now also repairs misspelled French medical terms ("ostéophite" becomes "ostéophyte", "glomérulone et frites" becomes "glomérulonéphrite"). The model repo moved its rules to [`regex-fixes/`](https://huggingface.co/Olicorne/parakeet-tdt-0.6b-v3-UltiMed-onnx/tree/main/regex-fixes) and added 25,045 medical-term rules, which run after its 3,428 drug-name rules (the drug rules are now merged: every misspelling of one drug is a single rule). Together they change none of the 602,813 correct labels of UltiMed and 1 of 1,662 French VoxPopuli transcripts, but they rewrite 77 of 100,000 French news sentences, almost all through the term rules, so expect an occasional overcorrection on general French text. The file served is now about 1 MB (brotli) instead of 190 KB, still fetched only once the setting is on, and applying the rules costs about 0.3 ms per transcript (measured in Node on the shipped rules).

The decoder **Debug** view now shows these rewrites too: the decoded pieces a rule replaced are struck through under a "→ replacement" label, and clicking one says which layer rewrote it, from what and with which rule, so a wrong word can be traced to either the decoder or the rules.

## Chunks are decoded together, with an fp32 decoder

Greedy decoding of a long recording now steps up to 8 chunks through the decoder at once instead of one after the other (groups of 1, 2, 4, then 8, so the first words still appear quickly). Beam search keeps the one-chunk-at-a-time path. The int8 decoder quantizes its activations with one scale per batch, so a chunk could come out differently depending on its neighbours; the decoder is therefore fp32 by default wherever the model source ships it (about 70 MB against 18 MB), and int8 otherwise. It runs on the CPU on both backends, where fp32 measured as fast as int8 at a batch of 8 (6.1 vs 6.4 ms per step), and the 3-minute test recording gives the same transcript at batch 1 and 8. On encoders exported with a padding mask, chunks of different lengths can now share one encoder batch too. The CLI gains `--decode-batch`; the OpenAI-compatible server and the CLI also default to the fp32 decoder.
